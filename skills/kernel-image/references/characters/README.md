# Characters — Identity Layer

Files in this directory define **who a character is** — silhouette,
proportions, signature features, clothing, colors, personality.

## Fixed Style, Variable Context

Every named character renders in exactly one style:
`references/anime/style-guide.md` — flat cel-shaded, bold linework,
traditional anime rendering language. This applies to the human-presenting
character (Lucy) and non-human characters (Wyatt, Benny, Void) alike, per
that file's "Non-Human Named Characters" section.

**The user cannot pick a different rendering style for a named character.**
What the user *can* change between requests:

- **Environment** — where the character is, what's around them.
- **Body position** — pose, action, gesture, expression.
- **Outfit** — a variation on their signature clothing, if requested (their
  default clothing from the identity file below still applies unless the
  user specifies otherwise).

The active image type (3D, Fine Art, Product) still governs the
*environment* and any *non-character* elements in the scene — it never
governs the character's own rendering.

Each turnaround PNG is a 4-view (front/3-4/side/back), plain-background
reference sheet generated by `scripts/generate-turnaround.ts` from the
character's identity file — a visual sanity check of the written spec, not
an input to future generation calls (the pipeline is text-prompt only, no
image references are sent to OpenRouter). Regenerate a character's sheet
after editing their identity file to confirm the change reads as intended.

## Why This Also Matters For Multi-Variant Consistency

A fixed identity file is what makes a character render the same way across
a batch of 3 generated variants — each generation call is independent and
stochastic, so freshly-written descriptive language ("a glamorous woman
with dark hair...") drifts between calls even when it's meant to describe
the same person. A detailed, fixed identity spec is far more constraining.
This is why the brief stage prefers matching a requested human figure to an
existing character here before writing new one-off descriptive language,
even when the user didn't ask for a specific named character by name — see
`references/stages/brief.md` step 5.
